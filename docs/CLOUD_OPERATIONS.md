## Durable private media

`PrivateBlobStorage` saves tenant-prefixed UUID objects, never overwrites names, and permits PNG/JPEG/WebP/PDF/CSV/XLSX up to 3 MB. This keeps proxied uploads below the hosting request-body limit. HTML and SVG uploads are rejected. The official pinned Python Blob SDK keeps credentials on the server.

A file URL is a five-minute signed capability generated while an authorized serializer accesses its file field. A serializer cannot issue a URL for a different tenant's path. Anyone holding that temporary URL can read that one file until expiry, so do not publish these URLs or place them in analytics. Images can render inline; documents download as attachments. Responses are private/no-store, nosniff and sandboxed. Links should be regenerated by reloading the authorized record after expiration. Existing media paths on a previous local disk are not automatically migrated.

Configuration: production `BLOB_READ_WRITE_TOKEN`. Development values live in ignored `.env.supabase.local` and `.env.blob.local`. If absent, the Vercel profile explicitly rejects uploads instead of writing to its temporary disk.

## Shared live updates

Housekeeping, kitchen and timed-session screens consume an authenticated HTTP event feed every five seconds while visible. Hidden tabs pause delivery; returning or reconnecting refreshes the current screen. Callbacks remain stable across renders. This is near-real-time polling, not a persistent WebSocket connection or a Redis service.

Existing broadcasts now persist to a shared PostgreSQL event table after transaction commit in the Vercel profile. Events are filtered by the tenant resolved from the authenticated session and by staff role/channel. A caller cannot select another tenant with a query parameter. KDS supports hot kitchen, cold prep, bar, pastry and all-station views. Housekeeping, KDS and timed sessions reconcile after reconnect. Normal mutations still use their existing REST endpoints.

The event table has an indexed tenant/channel/cursor query. Retention is one day. Tables have RLS enabled with no anonymous policies; only the server-side Django database role accesses them. An open screen consumes roughly 12 feed requests/minute; keep this in mind when assessing free hosting quotas. Docker retains its existing Channels transport; cross-tenant WebSocket authorization in that separate runtime should be reviewed before publicly exposing it.

## Scheduled maintenance

Supabase Vault stores `staywired_scheduler_secret`. Cron SQL reads it at invocation time and calls only the fixed API URL using a bearer header. The public endpoint rejects missing/wrong secrets and non-POST methods before doing any work. Extension request queues are not granted to anon/authenticated roles.

The shared runner executes in each active tenant schema:

| Job | Frequency |
| --- | --- |
| Timed session expiry warnings | Every minute |
| Auto-end sessions beyond their configured grace plus 30 minutes | Every five minutes |
| Previous-day property metrics | Once a day after 01:00 Nepal time |
| Event/audit retention cleanup | Each completed tick |

No outbound SMS/email campaigns, subscription invoice collection or automatic account suspensions are enabled by this configuration. Those require separate business/provider configuration. The old Beat entries referenced several nonexistent tasks and mixed shared/tenant work; Beat now uses the same tenant-aware maintenance runner for container deployments.

A PostgreSQL transaction advisory lock prevents concurrent ticks. Each job has a unique job/tenant/time-slot audit record. Jobs run within savepoints; errors are recorded by exception class without guest details or credentials. A transaction rollback permits a later tick to retry safely. A recorded failed slot is not silently rerun; investigate its cause and explicitly remove/reset that one failed run before retrying. Daily metrics use update_or_create, and task failures now propagate rather than appearing successful. The runner stops taking new work after 40 seconds; a larger tenant fleet should use a dedicated worker queue.

Event retention is one day; scheduler audit retention is seven days. Platform System Health shows the database, shared feed, recent scheduler success/failure, and private-media configuration instead of looking for nonexistent cloud Redis/Celery workers. A configured storage credential is shown as configured; it is not a continuous vendor availability test.

## Provision/redeploy

1. Save database, proxy, owner and storage values in the ignored backend local configuration.
2. Run `python scripts/supabase_manage.py migrate_schemas --shared --noinput`.
3. Run `python scripts/configure_vercel.py api` to transfer configuration through CLI stdin, without logging values.
4. Deploy the API and frontend from the reviewed Git commit.
5. Run `python scripts/supabase_manage.py shell -c "exec(open('scripts/configure_scheduler.py', encoding='utf-8').read())"` to idempotently configure the named cron job and Vault secret.
6. Verify HTTP success in pg_net responses and successful `ScheduledRun` records, not merely a successful cron dispatch.

To pause only maintenance, set the named cron job inactive with `cron.alter_job(job_id, active := false)`. Do not remove the storage store, tenant schemas or unrelated cron jobs. Rotating the scheduler secret requires updating both the API environment and the named Vault secret, followed by API redeployment.
